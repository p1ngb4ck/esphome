# hid: guide for AI agents

The transport-independent HID layer. Transports (`usb_hid`, `bt_hid`, `ble_client_hid`) own an `HIDInput`, feed it
report descriptors and reports, and know nothing about keys, layouts or pointers.

Files:
- `hid_parser.*`, `hid_item_value.h`, `hid_report_data.h`, `usages.h`, `usage_data.cpp`: report descriptor parsing
  into report maps; usages by page / id.
- `boot_report_decoder.*`: boot protocol reports for devices without a usable descriptor.
- `hid_input.*`: `HIDInput` (a `key_provider::KeyProvider`) - keys with their device, layouts (dead keys, compose,
  levels), text, pointer motion, controls, Num Lock / LEDs, the triggers.
- `gamepad.*`, `gamepad_drivers.cpp`: gamepad state, touchpads, outputs (rumble, player LED, light bar) and per-pad
  drivers.
- `hid_automation.h`, `hid_api.h`: actions, API actions (`api_actions: true`).
- `keys.py`: key names, aliases, `page:usage`; `layouts/`: one module per xkeyboard-config symbols file, generated by
  `script/generate_hid_layouts.py` (never edit them by hand). Layout data is built into flash at compile time.
- Platforms: `binary_sensor`, `event`, `sensor`, `text_sensor`.

Rules:
- Reports arrive on the transport's task (USB task, Bluetooth task); `HIDInput` is fed on the main loop - a
  transport queues the report and hands it over, it never calls triggers from its own task.
- No per-key or per-report allocation; layouts and key tables are const data in flash.
- Every key event carries its device, so several keyboards / remotes can be told apart and bound separately.
- LVGL consumes `HIDInput` through `lvgl/hid_input.py` and `lvgl_esphome.cpp` (`hid_keyboards`, `hid_pointers`,
  `key_bindings`, `remote_input`); while LVGL is paused, keys / text / pointer can be handed to another component
  (`set_paused_input`).
